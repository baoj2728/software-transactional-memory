Software Transactional Memory — Milestone Report

CMU 15-418/618 | November 23, 2026

Dylan Bao (jiayuanb) and Samuel Zhang (samuelz2)

Project: baoj2728.github.io/software-transactional-memory/ | Code: github.com/baoj2728/software-transactional-memory

Work completed

We have the main pieces of our C++ software transactional memory library implemented. We started with a global-lock version to get the transaction API working, then switched to a TL2-style design that allows concurrent execution. The library provides stm::atomic<T> variables and an atomic_run() wrapper. Each thread has its own transaction context with read and write sets. Writes stay in a local buffer until commit; shared variables have versioned locks, and transactions check read versions to detect conflicts.

The commit path now acquires the write-set locks using compare-and-swap, validates previous reads, publishes buffered writes, and releases the locks with updated versions. Failed reads and commits trigger a retry of the transaction body. We have also added cleanup for locks held by an aborted transaction. The core implementation is mostly done, but we still need more systematic testing and performance work.

Preliminary correctness checks

We ran a small local test harness against the current code using g++ and C++17. Each check passed in three repeated runs:

Progress against proposed goals

The main STM library and transaction API are at the prototype stage, roughly on schedule for the milestone. We expect to finish the planned correctness tests, shared-counter and bank-transfer benchmarks, and coarse- versus fine-grained-lock comparisons. The alternative eager-versioning and conflict-detection designs from the proposal are stretch goals; we will not prioritize them over a solid evaluation of TL2. If time allows, we will add a simple backoff policy and measure whether it helps under contention.

Remaining concerns

Our biggest concern is correctness under less predictable interleavings, especially conflict-heavy workloads, lock cleanup, and avoiding partial publication if a commit path fails. We also need to measure whether read/write-set bookkeeping and retries outweigh the concurrency benefit on small transactions. We will discuss the test plan and any remaining issues with course staff before finalizing the benchmarks.

Poster session plan

We plan to show graphs comparing STM, coarse-grained locking, and fine-grained locking on counter and bank-transfer workloads. The main plots will show transaction throughput versus thread count and abort rate versus contention. We also plan to show a small live demonstration of transfers across shared bank accounts, with the total balance remaining constant. The demonstration and exact plots will depend on the final testing results.
